# Principles

## Purpose

This document defines the fundamental principles that guide every decision made within Cosmos.

These principles are intended to remain stable throughout the lifetime of the project.

Whenever new features, systems or ideas are introduced, they should be evaluated against these principles.

---

# 1. The User Always Comes First

Cosmos exists to support its user.

The system should adapt to the user's way of thinking instead of forcing the user into predefined workflows.

The user owns their Cosmos.

---

# 2. Organize Meaning, Not Files

Cosmos does not use folders as semantic organization.

Cosmos does not infer meaning from source-code layout.

Cosmos organizes meaning.

Objects, Knowledge and Relationships are always more important than technical file structures.

The Files Tool may still perform explicit physical file operations inside the active Cosmos Project. That project-scoped capability never extends to arbitrary user files and never makes folder layout the semantic model.

---

# 3. Extensibility Before Complexity

Every part of Cosmos should be designed to grow.

New features should be added through extensions whenever possible instead of increasing complexity inside the core.

The Core should remain small, stable and understandable.

---

# 4. One System, Many Experiences

Everything inside Cosmos follows the same architecture.

Projects, Workspaces, Tools, Themes and future extensions all follow common principles.

Users should learn the system once and apply that knowledge everywhere.

---

# 5. Context Over Configuration

Cosmos should understand where the user is currently working.

Context should be inherited automatically whenever possible.

The user should rarely need to manually configure the same information twice.

---

# 6. Knowledge Never Gets Lost

Every meaningful idea deserves a place.

Knowledge should evolve through versions instead of being overwritten.

Original sources should remain traceable.

Nothing should disappear simply because it has been refined.

---

# 7. Human Decisions Stay Human

Artificial Intelligence assists.

Humans decide.

Cosmos may suggest, analyze, discover and explain.

Final decisions always belong to the user.

---

# 8. Progressive Discovery

The system should not interrupt the user unnecessarily.

Relationships, improvements and inconsistencies are collected over time.

Cosmos should present meaningful insights only when enough evidence exists.

Discovery is more valuable than interruption.

---

# 9. Consistency Before Features

Every new capability should feel like a natural extension of the existing system.

If a feature requires completely different concepts or behaviors, the architecture should be reconsidered before implementation.

---

# 10. Everything Is Connected

Projects, Knowledge, Objects, Resources, Workspaces and Tools are not isolated.

They form one connected ecosystem.

Cosmos should continuously reveal meaningful relationships between them.

---

# 11. Customization Without Fragmentation

Users are encouraged to customize their Cosmos.

Themes, Workspaces, Tools, Blueprints and Extensions should be freely replaceable.

Customization should never compromise the consistency of the overall system.

---

# 12. The Core Must Stay Stable

The Cosmos Core defines the contracts that every extension follows.

Extensions may grow without limits.

The Core should change only when absolutely necessary.

---

# 13. Build Once, Reuse Everywhere

Reusable concepts should always be preferred over special cases.

If something can become a reusable Tool, Workspace, Blueprint or Theme, it should.

Generalization creates long-term simplicity.

---

# 14. Evolution Over Perfection

Users should never feel forced to create perfect structures from the beginning.

Cosmos grows together with its user.

Projects, Knowledge, Tags and Relationships become more precise over time.

Starting is always more important than being perfect.

---

# 15. One Universal Object Model

Every independently addressable visible or interactive element inside Cosmos is represented by an Object.

System Tags compose Object roles and activate complete Property Schemas. Properties describe state. User Tags describe user-defined meaning and allow collections to emerge without a separate grouping system.

Themes represent Objects and define appearance only. They never define identity, capabilities or behavior.

Future growth should extend Objects, System Tags, Property Schemas, Prepared Structures and Extension Points before introducing another architectural system.
