# Prepared Structures

**Version:** 1.0
**Status:** Foundation
**Category:** Experience

---

# Purpose

This document defines how Cosmos prepares future extension structures for Projects, Nodes, Workspaces and other expandable Objects.

Prepared Structures allow users to extend an existing Project immediately without first creating folders, templates or organizational systems.

Cosmos prepares the structure.

The user decides whether to use it.

---

# Design Philosophy

Prepared Structures should be as complete as reasonably possible.

A newly created Project already contains the physical locations required for future Knowledge, Files, Themes, Workspaces, Templates and Extensions.

Prepared does not mean required.

Unused structures may remain empty indefinitely.

---

# Physical Existence

Every prepared structure exists physically.

Cosmos does not rely on hidden, virtual or lazily generated extension points.

If a structure belongs to an Object, it is created together with that Object.

This provides one observable Project reality for:

- users
- Tools
- Workspaces
- AI systems
- Git
- future Extensions

No Ghost Structures are permitted.

---

# Project Foundation

Every new Project receives a complete prepared foundation.

Typical top-level areas include:

- Knowledge
- Files
- Themes
- Workspaces
- Templates
- Extensions

System Tag combinations may activate additional prepared paths without introducing a separate Project class.

---

# Mirrored Project Structure

Prepared Structures mirror the real structural organization of the Cosmos.

They do not create unrelated duplicate hierarchies.

Example Cosmos structure:

```text
Mettventures
├── Lore
│   └── Gods
│       └── Druid God
└── Items
    └── Weapons
        └── Druid Dagger
```

The prepared Theme structure mirrors it:

```text
Themes/
└── Mettventures/
    ├── Lore/
    │   └── Gods/
    │       └── Druid_God/
    └── Items/
        └── Weapons/
            └── Druid_Dagger/
```

The same principle may apply to other relevant Project areas.

---

# Automatic Expansion

Prepared Structures expand whenever the real Cosmos structure expands.

Creating a structural Node creates the matching prepared path.

Moving a Node updates the mirrored path.

Removing or reorganizing Nodes must not leave the prepared structure inconsistent with the visible Cosmos.

---

# Targeted Preparation

Prepared Structures do not duplicate the complete Project architecture beneath every Node.

The Project owns the main prepared areas.

Individual Nodes receive only matching paths and extension points inside those areas.

This keeps the structure complete without unnecessary repetition.

---

# Prepared Theme Paths

Every Project receives its own Theme path.

```text
Themes/
└── Mettventures/
```

Every structural Node receives a matching location inside this Project Theme path.

The Graphics Workspace can therefore open the Project and immediately see the same hierarchy that exists in the Cosmos.

---

# Prepared Visual Components

Each relevant visual path may contain prepared component locations.

```text
Druid_Dagger/
├── Node_Template/
├── Conditions/
├── Animations/
├── Audio/
└── Assets/
```

These locations may remain empty. Their purpose is to make future customization immediately available.

---

# Complete Default Properties

A prepared visual Object begins from a complete Property Schema.

```text
Skin = Default Node Template
Condition = Standard
Animation = Static
Audio = Silent
```

The user may replace any Component later. Missing behavior is represented by explicit defaults rather than missing Properties.

---

# Workspace Projects

Projects identified through the `Workspace` System Tag receive prepared structures appropriate for Workspace development.

```text
Project + System + Workspace
```

may create:

```text
Themes/
└── Itembuilder_Workspace/
    └── Workspace_Template/
```

Future Workspace Objects, Tool Windows and visual Components extend this structure automatically.

---

# System Tag Awareness

Prepared Structures respond to the combined System Tags of the Project and its Objects.

Examples include:

- Project + Workspace
- Project + Theme
- Project + Game
- Project + Application
- Node + Tool
- Node + Workspace

Preparation emerges from the universal classification system.

---

# Graphics Workspace Integration

The Graphics Workspace should open any Project and immediately access its prepared visual structure.

Users should see:

- Project hierarchy
- matching Node Templates
- existing Skins
- Conditions
- Animations
- Audio
- Assets

No manual recreation of the Project organization is required.

---

# User Control

Automatic preparation never creates visual decisions on behalf of the user.

Cosmos creates paths, Templates and valid defaults.

The user chooses whether customization is needed, which Components are replaced and how far an override applies.

---

# AI Integration

Prepared Structures provide reliable context for AI systems.

AI receives predictable physical paths, matching Project hierarchy, existing Templates, complete Properties and relevant documentation.

Generated Components can therefore be placed correctly without inventing new organization.

---

# Experience Goals

Prepared Structures should always feel:

- invisible
- complete
- predictable
- reliable
- immediately useful

Users should experience that every Project is ready to grow before they need it to grow.

---

# Design Principles

Prepared Structures exist physically.

Prepared Structures mirror the real Cosmos structure.

Prepared does not mean required.

Cosmos creates the foundation.

The user controls the result.

Future expansion should never require rebuilding the Project structure.

---

# Scope

This document defines the Experience behavior of Prepared Structures. Structure Templates, Extension Points and future Extensibility systems are documented separately.
